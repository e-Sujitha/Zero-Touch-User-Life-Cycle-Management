# System Architecture

## Overview

The Zero-Touch AWS IAM User Lifecycle Management System follows a serverless, event-driven architecture.

Slack is used as the administrative interface. Commands submitted through Slack are sent to Amazon API Gateway, which invokes the appropriate AWS Lambda function.

The Lambda functions interact with AWS IAM, DynamoDB, Amazon SES, and other AWS services to complete the requested lifecycle operation.

---

## Architecture Components

### 1. Slack

Slack acts as the ChatOps interface for administrators.

The system supports commands such as:

```text
/onboard <username> <email>
/offboard <username>
/restore <username>
```

These commands provide a simple interface for initiating IAM lifecycle operations without requiring administrators to manually navigate through multiple AWS console pages.

---

### 2. Amazon API Gateway

API Gateway receives HTTP requests generated by the Slack slash commands.

Example flow:

```text
Slack
  ↓
HTTP POST
  ↓
API Gateway
  ↓
Lambda
```

API Gateway acts as the entry point between Slack and the AWS backend.

---

### 3. AWS Lambda

AWS Lambda contains the business logic for the lifecycle operations.

The project separates responsibilities into multiple functions:

```text
Onboarding Lambda
Offboarding Lambda
Restore Lambda
Permanent Deletion Lambda
```

This separation makes the system easier to maintain and allows each workflow to have its own permissions and responsibilities.

---

### 4. AWS IAM

AWS IAM is the primary identity management service used by the application.

The Lambda functions perform operations such as:

* Creating IAM users
* Checking whether users exist
* Creating access keys
* Deleting access keys
* Managing console access
* Managing policies
* Removing user access
* Deleting IAM users

During offboarding, the system applies an explicit deny policy to prevent further AWS activity during the cooling period.

---

### 5. Amazon DynamoDB

DynamoDB stores the lifecycle and audit information associated with IAM users.

The table is used to track states such as:

```text
ACTIVE
TOMBSTONE
DELETED_PERMANENTLY
```

The stored information can include:

* User ID
* Action
* Status
* Timestamp
* Created by
* Offboarded timestamp
* Scheduled deletion time

This provides a centralized record of lifecycle events.

---

### 6. Amazon SES

Amazon SES is used to send credential-related emails.

Credentials are intentionally not exposed through Slack responses.

The email workflow is:

```text
Lambda
  ↓
Amazon SES
  ↓
Verified Email Address
```

This keeps sensitive credential information outside the Slack channel.

---

### 7. Amazon EventBridge

Amazon EventBridge is responsible for triggering the scheduled cleanup workflow.

After a user enters the TOMBSTONE state, the system records a scheduled deletion time.

EventBridge periodically triggers the permanent deletion Lambda, which checks for expired records.

---

### 8. Amazon S3

Amazon S3 hosts the static audit dashboard.

The dashboard provides a visual representation of user lifecycle states and audit information.

The frontend consists of:

```text
HTML
CSS
JavaScript
```

---

### 9. Amazon CloudWatch

CloudWatch Logs provides visibility into Lambda executions.

It can be used to investigate:

* Successful executions
* Lambda errors
* IAM API failures
* DynamoDB failures
* SES errors
* Unexpected workflow behavior

# End-to-End Request Flow

## Onboarding

```text
Administrator
     ↓
Slack /onboard
     ↓
API Gateway
     ↓
Onboarding Lambda
     ↓
AWS IAM
     ↓
Create User + Credentials
     ↓
DynamoDB
     ↓
Record ACTIVE State
     ↓
Amazon SES
     ↓
Credential Email
     ↓
Slack Success Response
```

## Offboarding

```text
Administrator
     ↓
Slack /offboard
     ↓
API Gateway
     ↓
Offboarding Lambda
     ↓
AWS IAM
     ↓
Remove Access
     ↓
Apply AWSDenyAll
     ↓
DynamoDB
     ↓
TOMBSTONE State
     ↓
EventBridge
```

```text

     ↓

     ↓
API Gateway
     ↓
Restore Lambda

Remove Quarantine
     ↓
Generate New Credentials
     ↓

     ↓
Updated Credentials
```

# Design Principles

The architecture follows several important cloud engineering principles:

### Serverless

The backend uses managed AWS services instead of maintaining traditional servers.

### Event-Driven

Different events and scheduled triggers initiate the required workflows.

### Least Privilege

Lambda execution roles should contain only the permissions required for the operations they perform.

### Separation of Responsibilities

Onboarding, offboarding, restoration, and permanent deletion are handled independently.

### Auditability

Lifecycle changes are recorded in DynamoDB so that administrators can understand what happened and when.

### Security by Design

Offboarding immediately removes active access and places the user into a controlled quarantine state before permanent deletion.
